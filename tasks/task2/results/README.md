# Задание 2. booking-service и booking-history-service

Решения взяты из [ADR задания 1](../../task1/results/ADR.md). Здесь — то, как они реализованы, и что выяснилось на практике.

## Что сделано

| Компонент | Что делает |
| :- | :- |
| `booking-service` | gRPC-сервер по `booking.proto` (порт 9090). Вся логика бронирования: проверки, цена, сохранение в свою БД `booking-db`, публикация `BookingCreated` в Kafka. Данные пользователей, отелей, отзывов и промокодов получает из монолита по REST |
| `booking-history-service` | Читает `BookingCreated` из Kafka, хранит историю в своей БД `booking-history-db`, отдаёт историю и статистику по REST (порт 8086) |
| `contracts` | Общий модуль, только `.proto`: `booking.proto` (gRPC) и `booking_events.proto` (событие). Java-классы каждый сервис генерирует сам |
| Монолит | Не менялся. Прокси включён переменными `BOOKING_SERVICE_EXTERNAL_HOST/PORT`; `ddl-auto` переопределён на `update`, чтобы перезапуск не стирал данные |

Стек: Java 17, Spring Boot 3.2, grpc-spring-boot-starter, Spring Kafka, PostgreSQL, Caffeine, Resilience4j, MapStruct, Lombok.

## Стратегия миграции данных при запуске нового сервиса

**Владение.** После переключения бронированиями владеет `booking-service`: новые брони пишутся только в `booking-db`, монолит в свою таблицу `booking` больше не пишет.

**Почему перенос обязателен.** По условию список бронирований в монолите «работает как раньше». На деле прокси (`GrpcBookingService.listAll`) отправляет в gRPC и список. Без переноса старые брони пропали бы из `GET /api/bookings`. Это видно и в тестах: брони из фикстур лежат в старой таблице, а тест списка их ищет.

**Как переносим** ([migrate-bookings.sh](test/migrate-bookings.sh)):

1. Брони копируются из `booking` монолита в `booking-db` с сохранением `id`. Повторный запуск безопасен: уже перенесённые брони пропускаются (`ON CONFLICT (id) DO NOTHING`).
2. Счётчик `id` в `booking-db` сдвигается на 1000 выше максимального перенесённого. Брони, созданные монолитом в окне переключения, не пересекутся с новыми бронями сервиса. В выгрузке это видно: перенесённые брони имеют `id` 9–10, новые — от 1018.
3. Порядок при переключении:
   - основной проход;
   - переключение прокси переменными окружения и перезапуск монолита;
   - догоняющий проход тем же скриптом.
4. Откат: убрать переменные прокси и перезапустить монолит. Брони, созданные в `booking-service`, вернуть обратно тем же скриптом, поменяв источник и приёмник местами.
5. Старая таблица `booking` остаётся только для чтения на время стабилизации, затем удаляется.

**Предусловие.** У монолита `ddl-auto: create`, то есть каждый перезапуск стирает БД. Для миграции это недопустимо: переключение само требует перезапуска. В `docker-compose.yml` задано `SPRING_JPA_HIBERNATE_DDL_AUTO=update`. Схема создаётся, если её нет, и не удаляется. `validate`, как сначала записано в ADR, не подходит: на пустой БД монолит не стартует.

**История.** `booking-history-service` считает статистику с момента переключения. Старые брони в историю не переносятся: у реальных старых броней нет `createdAt`, статистику по дням из них не построить.

**Старые брони без даты.** Прокси монолита разбирает `created_at` через `Instant.parse`, поэтому пустая строка роняет весь список. Для перенесённых броней без даты сервис отдаёт `1970-01-01T00:00:00Z`.

## Стратегия To-Be

Целевая схема — диаграммы C4 в [ADR](../../task1/results/ADR.md#диаграммы-c4). Кратко:

- **Входная точка бронирований** — `booking-service`. Монолит пока остаётся фасадом и проксирует `/api/bookings` по gRPC. Позже прокси заменит BFF / API Gateway (задание 3).
- **Справочные данные** `booking-service` берёт из монолита по REST:
  - пять запросов идут параллельно;
  - таймаут 1 с;
  - один повтор и только на быстрые ошибки;
  - circuit breaker;
  - кэш с TTL: пользователь — 5 мин, отель — 1 ч, заполненность — 1 мин, доверие — 1 ч;
  - если монолит недоступен, отель, заполненность и доверие берутся из устаревшего кэша (не старше 24 ч). Пользователь из устаревшего кэша не берётся, а неизвестный пользователь получает отказ.
- **История.** Аналитика строится асинхронно по событиям в отдельном сервисе с отдельной БД. Боевая БД бронирований не нагружается.
- **Дальше по Strangler Fig** — выносить отзывы, отели, промокоды и пользователей. После выноса User и Hotel:
  - TTL заменить инвалидацией по событиям;
  - флаг `fullyBooked` заменить расчётом заполненности в `booking-service`.

## Решения, принятые при реализации

**Событие `BookingCreated` — Protobuf, отдельное сообщение, а не `BookingResponse`.** Ответ API и событие — разные контракты. Ответ API будет меняться под клиентов, событие — нет. В событии есть всё, что нужно аналитике, без обращения к другим сервисам:

- id брони, пользователя и отеля;
- `created_at` как `Timestamp`;
- цена до скидки, скидка и итог;
- промокод;
- снимок статуса пользователя и города отеля на момент брони.

Персональных данных в событии нет.

**Топик `booking.created`, ключ — `bookingId`, 3 партиции. Владелец топика — `booking-service`.** На практике всплыла гонка. `booking-history-service` стартовал раньше и сам создал топик автоматически, с одной партицией. Когда `booking-service` добавил ещё две, потребитель их не видел до обновления метаданных (по умолчанию 5 минут), и часть событий задерживалась. Исправление:

- потребителю запрещено создавать топики (`allow.auto.create.topics=false`);
- метаданные обновляются каждые 30 с.

**История хранит сырые события, статистика считается SQL-запросом.**

- Новый разрез — это новый `GROUP BY`, без миграции счётчиков. Так добавлены разрезы по дням и по городам.
- Идемпотентность простая: `booking_id` — первичный ключ, повторное событие пропускается.
- Когда объём вырастет настолько, что запросы на лету станут медленными, — материализованные представления или предрасчёт.

Эндпоинты: `GET /api/history?userId=`, `GET /api/stats/users`, `/api/stats/hotels`, `/api/stats/days`, `/api/stats/cities`.

**Ошибка отправки события не отменяет бронь.** Бронь уже сохранена. Ошибка пишется в лог, событие теряется. Ожидание метаданных Kafka ограничено 2 с, чтобы недоступная Kafka не задерживала ответ клиенту. При требовании «ни одного потерянного события» — transactional outbox.

**Неприменённый промокод не сохраняется в бронь.** Пустой `promoCode` в ответе — сигнал клиенту, что скидки нет.

## Изменения в тестах

- **Тест «все бронирования».** Теперь выполняется по gRPC напрямую в `booking-service`. Через монолит он не может пройти: прокси передаёт в protobuf `userId = null` и падает с NPE (HTTP 500). Это ограничение прокси, его исправит команда монолита. В [bookings-rest-monolith.txt](bookings-rest-monolith.txt) это видно.
- **Перенос данных.** Перед HTTP-тестами брони из фикстур переносятся тем же `migrate-bookings.sh`, что и при реальном переключении. Тестовые данные новых БД очищаются.
- **Фикстуры.** Раньше тесты «недоверенный отель» и «отель полностью забронирован» проходили по чужой причине: первый отель был закрыт, второй — недоверенный. Добавлены `test-hotel-4` (работает, мало отзывов) и `test-hotel-5` (работает, доверенный, мест нет). В логе `booking-service` видны правильные причины отказа: `HOTEL_NOT_TRUSTED` и `HOTEL_FULLY_BOOKED`.
- **Новые проверки:**
  - цена без промокода, с промокодом, VIP с VIP-промокодом (60 = 80 − 20);
  - истёкший промокод: бронь без скидки, промокод не сохранён;
  - заполненная дата создания;
  - отказ пользователю из чёрного списка;
  - появление исторической записи (асинхронно, ожидание до 20 с);
  - статистика по отелям;
  - отклонённые брони не попадают в историю.
- **Модульные тесты** сервисов выполняются при сборке Docker-образа (`gradle build`).
