## Изменения и примененные паттерны

### Проксирование и gRPC
* Запустил gRPC-сервер `booking-service` на порту `9090` по контракту `booking.proto`.
* Включил проксирование в монолите через переменные окружения. Запросы на создание бронирований теперь уходят на новый gRPC-сервер.
* Реализовал валидацию данных через асинхронные HTTP-запросы обратно к монолиту (проверка активности пользователей, черных списков и статуса отелей).

### Паттерн Transactional Outbox
* Чтобы данные не терялись при сбоях сети или брокера, применил паттерн **Transactional Outbox**.
* При создании бронирования сама запись (`BookingModel`) и событие для Kafka (`KafkaOutbox`) сохраняются в базу микросервиса атомарно, в одной ACID-транзакции.
* Фоновый воркер `_outbox_relay_worker` опрашивает таблицу outbox, отправляет сообщения в Kafka и отмечает их как обработанные. Использовал `with_for_update(skip_locked=True)`, чтобы избежать конкуренции потоков.

### Асинхронная аналитика
* Создал сервис `booking-history-service` (Kafka Consumer), который читает топик `booking-events`.
* Данные для аналитиков пишутся асинхронно в изолированную таблицу `processed_bookings`, полностью снимая нагрузку с боевой базы.

## Текущая проблема с листингом (Регрессия)

При интеграции возникла проблема с получением списка всех бронирований:
1. Запрос списка по конкретному пользователю (`http://localhost:8084/api/bookings?userId=test-user-3`) **работает корректно**.
2. Запрос на получение вообще всех бронирований приложения (`http://localhost:8084/api/bookings`) **выдает ошибку**. В старой базе данные по новым бронированиям уже недоступны, а в новом микросервисе этот сквозной эндпоинт изначально не планировался.

**Принятое решение:** 
Не тратить время на поиск и исправление этой ошибки в коде монолита. В контексте миграции это нецелесообразно. Быстрее и правильнее сразу расширить Protobuf-контракт в новом микросервисе, добавить туда метод для общего листинга и полностью перевести эту логику на `booking-service`.

## Стратегия миграции данных

Миграция разделена на 4 шага для обеспечения Zero Downtime:

1. **Двойная запись и проксирование**: Новые бронирования создаются в базе `booking-service`. Монолит ходит в микросервис за актуальными данными.
2. **Перенос истории**: Скрипт асинхронно, пачками переносит старые записи из базы монолита в базу `booking-service`.
3. **Сверка**: Фоновый процесс проверяет контрольные суммы в обеих базах, чтобы исключить расхождения.
4. **Отключение**: Чтение и запись полностью переходят на микросервис. Код и таблицы бронирований удаляются из монолита.
