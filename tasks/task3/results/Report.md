# Отчет по задаче 3: Внедрение GraphQL Federation и ACL

## Что было сделано:
1. **Развернут GraphQL Gateway.** Он принимает запросы от клиента и маршрутизирует их в нужные микросервисы (субграфы).
2. **Созданы субграфы ooking-subgraph и hotel-subgraph.** Они отвечают за свои сущности.
3. **Убраны заглушки.** Теперь ooking-subgraph при запросе бронирований не возвращает фейковые данные, а делает реальный HTTP-запрос (через etch) к нашему Java-сервису ooking-service по адресу http://booking-service:8085/api/bookings/{userId}.
4. **Реализован ACL (контроль доступа).** 
   В резолвере ookingsByUser мы добавили проверку: Gateway пробрасывает заголовок x-user-id в субграф. В коде мы сравниваем этот ID с тем userId, который клиент просит в GraphQL-запросе. Если они не совпадают, выбрасывается ошибка "Доступ запрещен". Пользователь может видеть только свои бронирования.
5. **Исправлена ошибка с отсутствующим полем hotel.** Мы добавили резолвер в ooking-subgraph, который формирует объект отеля из hotelId. Gateway подхватывает его и автоматически делает запрос в hotel-subgraph, чтобы достать название и город.

## Как проверялось:
*   **Успешный вызов (Allow):** Отправляли запрос с заголовком x-user-id: test-user-2 и просили брони для userId: "test-user-2". Вернулись реальные данные, включая информацию об отеле.
*   **Отказ (Deny):** Отправляли запрос с заголовком x-user-id: test-user-2, но просили брони для userId: "test-user-1". Сработал ACL, вернулась ошибка доступа.
