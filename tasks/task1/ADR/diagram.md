# ADR-001: Поэтапная миграция Hotelio на микросервисную архитектуру с использованием паттерна Strangler Fig

**Автор:** Лукин Михаил
**Дата:** 21.09.2026

## Контекст

Монолит столкнулся с различными проблемами:

- Масштабирование. Сложно масштабировать монолитное приложение
- Разработка. Новый функционал внедрят дольше. Есть риски сломать что-то в другом месте
- Отказоустойчивость. При отказе одного из компонентов есть риск отказа всей системы

Необходимо разделить приложение на разные микросервисы. При этом решить проблемы описанные выше. При этом сервисом уже
пользуются и нельзя менять существующие контракты.

## Функциональные требования

| № | Действующие лица или системы | Use Case                      | Описание                                                                                                            |
|--:|------------------------------|-------------------------------|---------------------------------------------------------------------------------------------------------------------|
| 1 | Пользователь                 | Ищет и просматривает отели    | Пользователь отправляет запрос на поиск отелей, смотрит карточки отелей.                                            |
| 2 | UserService                  | Проверяет статус пользователя | Система проверяет статус пользователя.                                                                              |
| 3 | Пользователь                 | Управляет бронированием       | Пользователь отправляет запрос на бронирование. Так же может посмотреть на свои бронирования. Может отменить бронь. |
| 4 | Пользователь                 | Использует промокод           | Пользователь отправляет запрос на применение промокода.                                                             |
| 5 | Пользователь                 | Смотрит отзывы                | Пользователь отправляет запрос на просмотр рейтинга отеля.                                                          |

## Нефункциональные требования

| № | Требование                                                                                                                            |
|--:|---------------------------------------------------------------------------------------------------------------------------------------|
| 1 | **Масштабируемость:** новые микросервисы должны масштабироваться независимо от монолита.                                              |
| 2 | **Доступность:** 99,9% для новых сервисов. При недоступности монолита допускается частичная деградация сценариев.                     |
| 3 | **Изоляция данных:** у каждого нового сервиса своя база данных. Прямые запросы в чужие БД запрещены.                                  |
| 4 | **Совместимость:** существующие REST-контракты должны сохраняться через API Gateway/BFF. Изменения выполняются через версионирование. |
| 5 | **CI/CD:** отдельные пайплайны для каждого сервиса, сборка Docker-образов, дальнейший переезд в облако.                               |

## Решение

Выбран паттерн **Strangler Fig**. Монолит продолжает работать, но постепенно «обвивается» новыми сервисами. На
промежуточном этапе через два месяца выделяется наиболее критичный сервис:

- **Booking Service** - создание и просмотр бронирований. Позволяет независимо масштабировать критичный транзакционный
  сценарий.

Дополнительно вводится **BFF**. Он маршрутизирует запросы к новым сервисам и
монолиту, адаптирует API под веб и мобильные клиенты, обеспечивает аутентификацию и ограничение скорости запросов.

Монолит не дорабатывается. Новая функциональность пишется только в Booking Service. Пользователи,
промокоды, отзывы и старые бронирования пока остаются в монолите. Booking Service синхронно вызывает монолит для
проверки пользователя и промокода.

**Контекст решения.** Пользователь взаимодействует с BFF. BFF направляет запросы бронирования
в Booking Service, а все остальные запросы - в монолит. Booking Service при создании брони обращается к монолиту для
проверки отеля, пользователя и промокода.

### **Компоненты системы (через 2-3 месяца)**

| Компонент            | Что делает                                                           |
|----------------------|----------------------------------------------------------------------|
| **Booking Service**  | Новый сервис. Бронирование. Своя база данных.                        |
| **Монолит**          | Пользователи, отели, промокоды, отзывы. Старую логику не трогаем.    |
| **BFF**              | Прослойка между фронтендом и сервисами. Адаптирует API под клиентов. |
| **Apollo Gateway**   | Единая точка входа для GraphQL. Объединяет схемы субграфов.          |
| **Booking Subgraph** | GraphQL-адаптер над Booking Service                                  |
| **Hotel Subgraph**   | GraphQL-адаптер над монолитом (отели)                                |
| **Kafka**            | Для фоновых и планируемых задач                                      |

### **Недостатки, ограничения, риски**

- Нужно разрабатывать новый микросервис и поддерживать монолит
- Временно возрастут траты на железо
- Некоторые данные будут дублироваться
- Данные будут идти чуть дольше, т.к будут использовать промежуточные слои, а не идти напрямую, как сейчас

### **Альтернативное решение**

Произвести переход на микросервисную архитектуру сразу

| Что сравниваем       | Strangler Fig (выбрали)                                                                                                                                              | Полный переход (альтернатива)                                                     |
|:---------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------|
| Сложность реализации | Средняя.Первый микросервис будет сделать тяжелее всего.<br/> Дальше можно будет использовать текущие наработки. Улучшать будущие сервисы на основе полученного опыта | Высокая. Огромная нагрузка на командй.Требуется полный пересмотр релизного цикла. |
| Отказоустойчивость   | Низкая.При отказе микросервиса все остальное будет работать. Отказ монолита = отказ всей системы. При полном переходе станет Высокой                                 | Высокая. Каждый микросервис может работать без участия других                     |
| Масштабируемость     | Низкая, пока существует монолит. При полном переходе станет Высокой                                                                                                  | Высокая. Каждый компонент может масштабироваться отдельно                         |
