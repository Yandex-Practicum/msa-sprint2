### <a name="_3bfxc9a45514"></a>**Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Пользователь (гость сайта) | Просмотр отзывов об отеле | Пользователь открывает страницу отеля и видит список отзывов других гостей с оценками и комментариями |
| 2 | Пользователь (гость сайта) | Просмотр среднего рейтинга отеля | Пользователь видит агрегированный рейтинг отеля на основе всех отзывов |
| 3 | Авторизованный пользователь | Добавление отзыва | Пользователь, совершивший бронирование, может оставить отзыв об отеле с оценкой и текстовым комментарием |
| 4 | BookingService | Проверка репутации отеля | При создании бронирования система проверяет, не заблокирован ли отель из-за низкого рейтинга |
| 5 | Администратор | Модерация отзывов | Администратор может скрыть или удалить некорректные отзывы |
| 6 | API Gateway | Маршрутизация запросов | Запросы вида `/api/reviews/*` направляются в отдельный микросервис Review Service |

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | **Доступность**: сервис отзывов должен быть доступен 99.9% времени. Отказ сервиса не должен блокировать процесс бронирования |
| 2 | **Производительность**: время ответа на запрос отзывов не должно превышать 200 мс (p95) |
| 3 | **Масштабируемость**: сервис должен поддерживать горизонтальное масштабирование при росте нагрузки |
| 4 | **Независимость развёртывания**: обновление Review Service не должно требовать перезапуска монолита |
| 5 | **Согласованность данных**: рейтинг отеля должен быть актуальным с задержкой не более 5 секунд после добавления отзыва |
| 6 | **Безопасность**: добавление отзывов доступно только авторизованным пользователям с валидным токеном |
| 7 | **Наблюдаемость**: сервис должен предоставлять метрики (Prometheus), логи и трейсинг для мониторинга |
| 8 | **Отказоустойчивость**: при недоступности Review Service бронирование должно продолжаться без проверки репутации (graceful degradation) |

### <a name="_qmphm5d6rvi3"></a>**Решение**

#### Обоснование выбора

Для миграции выбран модуль **ReviewService** по следующим причинам:

1. **Отсутствие зависимостей** — ReviewService не зависит от других модулей монолита. Он предоставляет данные (отзывы и рейтинги), но не потребляет данные из других сервисов для своей основной логики.

2. **Чёткие границы API** — все эндпоинты отзывов находятся под префиксом `/api/reviews/*`, что позволяет легко настроить маршрутизацию через API Gateway.

3. **Низкий бизнес-риск** — временная недоступность сервиса отзывов не блокирует ключевой бизнес-процесс (бронирование). Система может работать в режиме graceful degradation.

4. **Простота миграции данных** — модель данных отзывов простая (таблицы `review`, `rating`), не имеет сложных связей с другими сущностями.

5. **Отработка паттерна** — вынос ReviewService позволяет отработать паттерн Strangler Fig на простом примере перед миграцией более критичных сервисов.
