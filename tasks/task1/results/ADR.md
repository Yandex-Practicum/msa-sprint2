### **Название задачи:** Переход Hotelio с монолита на микросервисы (Strangler Fig)
### **Автор:** Иван Бусаров
### **Дата:** 21.10.2026

### **Контекст**

Hotelio это монолит на Spring Boot с одной базой PostgreSQL. В базе лежит все сразу: пользователи, отели, бронирования, промокоды, отзывы. Пользователей около миллиона, основная нагрузка на поиск и бронирование. Команда маленькая, два Java-разработчика, архитектор, фронтенд, DevOps, тестировщик и продакт.

Сначала поднял монолит, залил фикстуры из test/ и прогнал regress.sh. Все тесты прошли, лог в test-log.txt. Потом посмотрел код.

Кроме проблем из описания задачи (все связано со всем, нельзя масштабировать отдельный кусок, команды мешают друг другу, нет BFF) нашел вот что:

- BookingService при каждом бронировании синхронно дергает UserService, HotelService, ReviewService и PromoCodeService. Это главный узел связности.
- Чтобы понять, надежный ли отель, на каждую бронь из базы читаются все его отзывы и считается средний рейтинг.
- Поле discountPercent называется процентом, но туда пишется абсолютная скидка (finalPrice = basePrice - discount).
- Цена зашита в код, 100 или 80 для VIP. От отеля не зависит.
- createdAt у брони не заполняется, в ответе null (видно в test-log.txt).
- ddl-auto: create, при каждом рестарте схема пересоздается и данные пропадают.
- Ошибки валидации кидаются как IllegalArgumentException, наружу уходит 500, а не 4xx.
- Авторизации нет. userId передается параметром, забронировать можно за кого угодно.
- Документация расходится с кодом. У Hotel нет полей name и pricePerNight, хотя в architecture/readme.md они есть.

### **Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
|:-:|:-|:-|:-|
| 1 | Пользователь | Создать бронирование | Проверяем пользователя (активен, не в блэклисте), отель (работает, есть места, хорошие отзывы), промокод. Считаем цену, сохраняем |
| 2 | Пользователь | Посмотреть свои бронирования | Список по userId |

| 4 | Аналитики | Статистика по бронированиям | По пользователям, отелям, дням, без доступа к боевой базе |
| 5 | Фронтенд | Личный кабинет | Брони и данные отеля одним запросом, только свои |

### **Нефункциональные требования**

| № | Требование |
|:-:|:-|
| 1 | Переезд без остановки, старый REST монолита продолжает работать |
| 2 | Бронирование масштабируется отдельно от остального |
| 3 | У каждого вынесенного сервиса своя база |
| 4 | Статистика считается асинхронно и не грузит боевую БД |

### **Решение**

Идем по Strangler Fig, выносим по одному модулю, остальное пока живет в монолите.

Начинаем с бронирования. Почему:

- основная нагрузка и пики как раз на бронировании, его и надо масштабировать первым
- BookingService завязан на все остальные модули. Если вынести его, остальные станут по сути справочниками, которые только отдают данные
- в монолите уже есть точка переключения, BookingServiceProxyConfig. Если задать BOOKING_SERVICE_EXTERNAL_HOST, вместо локального сервиса подставляется gRPC клиент. Откатиться можно, просто убрав переменную

Думал начать с отзывов или промокодов, их вынести проще. Но главную проблему с нагрузкой и связностью бронирования это не решает.

Что будет через пару месяцев (диаграмма в to-be.puml):

- booking-service. Новый сервис, gRPC по booking.proto, своя база. Логику переносим как есть, данные о пользователе, отеле, промокоде и отзывах пока берем из монолита по REST. После создания брони отправляем событие BookingCreated в Kafka.
- booking-history-service. Читает события из Kafka и копит статистику у себя в базе. Аналитики ходят туда, а не в боевую БД.
- Монолит остается фасадом. /api/bookings проксирует в booking-service, остальное работает как раньше. Новые фичи в монолит не пишем.
- GraphQL (Apollo Federation) для фронта. Подграф бронирований ходит в booking-service, подграф отелей в монолит.
- Потом так же выносим отели вместе с отзывами, промокоды и пользователей.

План миграции:

1. Регресс зеленый на монолите, это эталон поведения. Убрать ddl-auto: create.
2. Написать booking-service, перенести логику бронирования один в один.
3. Скопировать таблицу booking из базы монолита в базу booking-service, схема та же.
4. Включить прокси в монолите, прогнать регресс. Если что-то сломалось, выключить.
5. Добавить события в Kafka и booking-history-service.
6. Перевести фронт на GraphQL.
7. Docker, Helm, CI/CD, потом Istio для canary релизов.
8. Когда все клиенты ходят в новый сервис, удалить бронирование из монолита вместе с таблицей.
9. Повторить для следующих модулей.

### **Альтернативы**

- Переписать все разом. Команда маленькая, долго без релизов, большой риск. Не подходит.
- Общая база для монолита и booking-service. Быстрее, но связность через схему остается и нагрузку не разнести.
- Считать статистику прямо в booking-service. Лишняя ответственность для только что вынесенного сервиса, поэтому отдельный сервис через Kafka.
- Только API Gateway без BFF. Не решает задачу собрать данные из нескольких доменов одним запросом.

### **Недостатки, ограничения, риски**

- booking-service на каждую бронь делает 6-7 синхронных запросов в монолит. Растет задержка, и монолит остается точкой отказа. Потом нужен кэш или свои копии данных по событиям.
- Если Kafka лежит, событие теряется (сама бронь при этом создается). По хорошему нужен outbox.
- На переключение нужно короткое окно, когда брони пишутся только в новый сервис, иначе данные разъедутся.
- Статистика обновляется не сразу, а с небольшой задержкой.
- Kafka, Kubernetes, Istio, все это ложится на одного DevOps.
- Баги монолита (скидка, createdAt, 500 вместо 4xx) переносим как есть, чтобы не сломать регресс. Чинить отдельно.
