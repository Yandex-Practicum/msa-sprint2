# ADR-001: Выбор первого модуля для выноса из монолита

## Статус

Принято

## Контекст

Система Hotelio реализована как Java Spring Boot монолит, включающий пять основных модулей:

- `BookingService` — создание и обработка бронирований
- `UserService` — проверка статуса пользователей
- `HotelService` — информация об отелях
- `PromoCodeService` — валидация промокодов
- `ReviewService` — управление отзывами и рейтингами

Необходимо начать миграцию на микросервисную архитектуру по паттерну **Strangler Fig**, выбрав один модуль для первоначального выноса.

### Критерии выбора первого кандидата:

1. **Чёткие границы контекста** — низкая связность с другими модулями
2. **Возможность независимого масштабирования** — высокая нагрузка на чтение
3. **Низкий риск критического сбоя** при миграции
4. **Минимальное влияние на основной бизнес-процесс** (бронирование и оплата)

## Рассмотренные варианты

### Вариант A: BookingService

- **Плюсы:** Критически важен для бизнеса
- **Минусы:** Максимальная связность (зависит от User, Hotel, Promo, Review). Высокий риск при выносе первым. Любая ошибка блокирует основной бизнес-процесс.

### Вариант B: UserService

- **Плюсы:** Используется всеми модулями
- **Минусы:** Требует сложной миграции сессий и токенов аутентификации. Становится единой точкой отказа.

### Вариант C: ReviewService

- **Плюсы:** Чёткая граница (отзывы и рейтинги). Высокая частота чтений, низкая частота записей. Ошибка не блокирует бронирование.
- **Минусы:** `BookingService` использует его для валидации минимального рейтинга.

## Решение

Выбран **ReviewService** в качестве первого кандидата на вынос.

## Обоснование

1. **Низкая связность:** `BookingService` использует `ReviewService` только для проверки минимального рейтинга перед бронированием. Это взаимодействие легко заменить на HTTP-вызов или чтение из кэша.
2. **Паттерн доступа:** Высокая частота чтений (просмотр отелей) и низкая частота записей (создание отзывов) идеально подходят для первого шага масштабирования и выноса в отдельную БД.
3. **Безопасность миграции:** Ошибка в сервисе отзывов не блокирует бронирование. Можно реализовать graceful degradation — если сервис недоступен, бронирование разрешается, но рейтинг не показывается.
4. **Независимая разработка:** Команда может работать над отзывами независимо от команды бронирований.

## Последствия

- Снижается нагрузка на монолит (основной трафик — чтение отзывов).
- Появляется возможность независимо масштабировать компонент отзывов.
- Закладывается фундамент для дальнейшего выноса других сервисов.
- Требуется реализовать механизм синхронизации рейтинга между монолитом и новым сервисом на время миграции.
