# ADR-002: Выбор протокола и подхода к интеграции Review Service

## Статус

Принято

## Контекст

При выносе `ReviewService` из монолита необходимо выбрать:

1. **Протокол взаимодействия** с внешними клиентами (через API Gateway)
2. **Способ интеграции** с монолитом (для валидации рейтинга при бронировании)
3. **Механизм синхронизации данных** на время миграции

Система использует стек: Java Spring Boot, PostgreSQL, Kafka, Docker. Целевая архитектура предполагает Service Mesh, метрики, трассировку и GraphQL для фронтенда.

## Рассмотренные варианты

### Сравнение протоколов взаимодействия

| Критерий                             | Вариант A: REST (HTTP/1.1 + JSON)                               | Вариант B: gRPC (HTTP/2 + Protobuf)                                        | Вариант C: GraphQL                                  |
| :----------------------------------- | :-------------------------------------------------------------- | :------------------------------------------------------------------------- | :-------------------------------------------------- |
| **Производительность**               | Средняя. Текстовый JSON, overhead заголовков HTTP/1.1.          | Высокая. Бинарный Protobuf, мультиплексирование HTTP/2, строгая типизация. | Средняя. Гибкость запросов, но overhead на парсинг. |
| **Сложность разработки**             | Низкая. Стандарт для Web, легко тестировать через curl/Postman. | Выше. Требует генерации кода из `.proto`, настройки gRPC-клиентов.         | Средняя. Требует знания GraphQL Schema и resolvers. |
| **Совместимость с Web**              | Отличная. Нативная поддержка браузерами.                        | Ограниченная. Требует gRPC-Web или трансляции на API Gateway.              | Хорошая. Нативная поддержка через Apollo/Relay.     |
| **Контракт (API Contract)**          | OpenAPI/Swagger, требует ручного поддержания.                   | Единый источник истины (`.proto`), автогенерация клиентов.                 | GraphQL Schema, автогенерация типов для фронтенда.  |
| **Экосистема и инструменты**         | Огромная база готовых решений.                                  | Растущая, требует специфичных знаний.                                      | Зрелая для фронтенда, но менее для бэкенда.         |
| **Соответствие целевой архитектуре** | Соответствует текущему стеку.                                   | Соответствует целевому Service Mesh.                                       | Соответствует цели "GraphQL для фронтенда".         |

### Сравнение подходов к интеграции с монолитом

| Критерий                   | Синхронный (HTTP/gRPC)                                 | Асинхронный (Kafka Events)                                    | Гибридный                |
| :------------------------- | :----------------------------------------------------- | :------------------------------------------------------------ | :----------------------- |
| **Согласованность данных** | Строгая (strong consistency).                          | Eventual consistency.                                         | Компромисс.              |
| **Отказоустойчивость**     | Низкая. Падение Review Service блокирует бронирование. | Высокая. События буферизуются в Kafka.                        | Высокая с кэшем.         |
| **Сложность реализации**   | Низкая. Простой HTTP-запрос.                           | Высокая. Нужна обработка Dead Letter Queues, идемпотентность. | Средняя.                 |
| **Производительность**     | Зависит от latency сети.                               | Очень высокая для записи.                                     | Высокая при кэшировании. |

## Решение

Принят **гибридный подход с приоритетом REST на первом этапе**:

1. **Внешний API (Web-клиент ↔ API Gateway ↔ Review Service):** **REST (HTTP/1.1 + JSON)**
   - Обеспечивает простоту интеграции с фронтендом
   - Легкость отладки и тестирования на стартовом этапе
   - Соответствие текущему стеку монолита

2. **Внутреннее взаимодействие (Monolith ↔ Review Service):** **REST (HTTP/1.1 + JSON)** на первом этапе
   - Ускорение разработки и онбординга
   - Возможность быстро переключиться на gRPC в будущем без изменения внешнего контракта

3. **Асинхронная синхронизация данных:** **Kafka Events**
   - События `ReviewCreated`, `ReviewUpdated`, `RatingUpdated` публикуются в Kafka
   - Монолит подписывается на события для обновления локального кэша рейтингов
   - Обеспечивает eventual consistency без блокировок

## Обоснование выбора

1. **Баланс скорости и качества:** REST позволяет быстро запустить сервис и начать получать обратную связь, не вкладываясь в сложную инфраструктуру gRPC на старте.
2. **Эволюционность архитектуры:** Внешний REST-контракт остаётся стабильным для клиентов. Внутреннее взаимодействие может быть переведено на gRPC позже, когда появится Service Mesh.
3. **Соответствие целевой архитектуре:** Kafka уже используется в инфраструктуре Hotelio, поэтому интеграция через события не требует новых технологий.
4. **Упрощение миграции:** Синхронные вызовы REST проще отлаживать при двойной записи (Dual-Write) и переключении трафика по паттерну Strangler Fig.

## Последствия

### Положительные:

- Упрощается онбординг разработчиков и тестирование нового сервиса
- API Gateway единообразно маршрутизирует весь внешний трафик как HTTP/REST
- Заложен фундамент для будущего перехода на gRPC внутри периметра доверия
- Kafka-события обеспечивают отказоустойчивость и масштабируемость

### Отрицательные:

- Временное увеличение latency из-за синхронных HTTP-вызовов между монолитом и Review Service
- Необходимость поддержания eventual consistency через Kafka
- Дублирование данных (рейтинг в монолите и в Review Service) на время миграции

### Митигация рисков:

- Внедрение кэша (Redis) для рейтингов в монолите, обновляемого через Kafka-события
- Мониторинг latency и error rate для быстрого обнаружения проблем
- План миграции на gRPC после внедрения Service Mesh (этап 2)
