# ADR-003: План миграции Review Service по паттерну Strangler Fig

## Статус

Принято

## Контекст

После выбора `ReviewService` для выноса и определения протоколов взаимодействия (ADR-001, ADR-002), необходимо спланировать поэтапную миграцию по паттерну **Strangler Fig**.

Цель: плавно перевести функционал отзывов из монолита в отдельный микросервис без остановки работы системы и с минимальным риском для пользователей.

## Решение: 5-этапный план миграции

### Этап 1: Подготовка инфраструктуры (Недели 1-2)

- Создание нового репозитория/модуля `review-service`
- Настройка CI/CD пайплайна (сборка, тесты, деплой)
- Создание Docker-контейнера для нового сервиса
- Развёртывание отдельной схемы/БД `review_db` в PostgreSQL
- Настройка мониторинга (метрики, логи, трассировка)

**Критерий готовности:** Сервис развёрнут в staging-окружении, БД создана, CI/CD работает.

### Этап 2: Миграция данных и Dual-Write (Недели 3-4)

- Реализация скрипта миграции исторических данных из `monolith_db` в `review_db`
- Настройка **Dual-Write** в монолите: при создании/изменении отзыва запись идёт и в старую БД, и (асинхронно через Kafka) в новый `Review Service`
- Настройка Kafka-продюсера в монолите для публикации событий `ReviewCreated`, `ReviewUpdated`
- Реализация Kafka-консьюмера в `Review Service` для применения событий

**Критерий готовности:** Все новые отзывы дублируются в обе системы. Расхождение данных < 0.1%.

### Этап 3: Переключение чтения (Неделя 5)

- Настройка API Gateway: маршрутизация всех `GET /api/reviews/*` запросов напрямую в новый `Review Service`
- Монолит продолжает принимать `POST/PUT` запросы на отзывы, но дублирует их в новый сервис
- Мониторинг расхождений данных между старой и новой БД
- Настройка кэша (Redis) для рейтингов в монолите, обновляемого через Kafka

**Критерий готовности:** 100% чтений отзывов идут через новый сервис. Latency < 200ms. Error rate < 0.1%.

### Этап 4: Переключение записи и валидации (Недели 6-7)

- Маршрутизация `POST/PUT /api/reviews/*` через API Gateway в новый `Review Service`
- Изменение `BookingService` в монолите: вместо прямого SQL-запроса к таблице отзывов, он делает HTTP-запрос к `Review Service` для проверки рейтинга отеля перед бронированием
- Отключение Dual-Write в монолите (запись идёт только в `Review Service`)

**Критерий готовности:** 100% записей и валидаций идут через новый сервис. Бронирования работают корректно.

### Этап 5: Удаление старого кода (Неделя 8)

- Полное отключение Dual-Write в монолите
- Удаление таблиц отзывов из `monolith_db` (после архивации)
- Удаление кода `ReviewService` из монолита
- Удаление HTTP-клиента для вызова `Review Service` из `BookingService` (замена на чтение из кэша)
- Архивация старых данных в холодное хранилище (при необходимости)

**Критерий готовности:** В монолите нет кода и данных отзывов. Все операции идут через `Review Service`.

## Альтернативные сценарии и откат

### План отката (Rollback):

- На любом этапе можно переключить API Gateway обратно на монолит
- Dual-Write гарантирует, что данные в монолите всегда актуальны до Этапа 4
- Kafka-события позволяют восстановить данные в `Review Service` при сбое

### Метрики успеха:

- Latency API отзывов < 200ms (p95)
- Error rate < 0.1%
- Расхождение данных между старой и новой БД = 0% (после Этапа 4)
- Время деплоя нового сервиса < 10 минут

## Последствия

- Риск простоя системы минимизирован благодаря поэтапному переключению
- Команда получает опыт миграции, который можно применить к другим сервисам
- Закладывается основа для дальнейшего разделения монолита
