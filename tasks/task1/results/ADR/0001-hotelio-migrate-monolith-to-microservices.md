# ADR 001. Миграция монолита Hotelio на микросервисную архитектуру (поэтапно, Strangler Fig)

| | |
|---|---|
| **Название задачи** | Проработка миграции от монолита к микросервисам |
| **Автор** | Архитектурная команда Hotelio |
| **Дата** | 2026-09-07 |

---

## 1. Контекст

Hotelio - платформа бронирования отелей. Бизнес-логика реализована в едином Java
Spring Boot монолите (`hotelio-monolith`), который отдаёт REST API и использует одну
базу PostgreSQL. С ростом бизнеса накопились архитектурные и операционные проблемы,
требующие перехода на микросервисы.

Анализ кода выполнен в рамках задания: прочитан исходный код (controllers,
services, repositories, entities), проанализирована схема БД, запущено приложение и
прогнаны регрессионные тесты (`test/regress.sh`). Результаты
проверки см. в `test-log.txt`.

### 1.1. Состав монолита

| Модуль | Контроллер | Зависит от (по коду) | Собственные данные |
|---|---|---|---|
| **Booking** (`BookingService`) | `BookingController` | User, Hotel, Review, PromoCode + `BookingRepository` | `booking` |
| **User** (`AppUserService`) | `AppUserController` | - (только `AppUserRepository`) | `app_user` |
| **Hotel** (`HotelService`) | `HotelController` | - (только `HotelRepository`) | `hotel` |
| **PromoCode** (`PromoCodeService`) | `PromoCodeController` | **User** (для проверки VIP-статуса) | `promo_code` |
| **Review** (`ReviewService`) | `ReviewController` | - (только `ReviewRepository`) | `review` |

REST-эндпоинты перечислены в `architecture/readme.md` и полностью покрыты
регрессионными тестами `test/`.

Основной бизнес-сценарий - `POST /api/bookings` - синхронно вызывает все 4
сервиса монолита: валидация пользователя → проверка отеля (operational /
fully-booked) → проверка доверия по отзывам (trusted) → применение промокода →
расчёт цены → запись в `booking`.

## 2. Функциональные требования

| № | Действующие лица или системы | Use Case | Пошаговое описание |
| :-: | :- | :- | :- |
| 1 | Пользователь | Создать бронирование | 1. Отправляет `POST /api/bookings?userId&hotelId[&promoCode]`.<br>2. Система проверяет активность пользователя и чёрный список.<br>3. Система проверяет отель (operational, не fully-booked).<br>4. Система проверяет доверие отзывам (avg ≥ 4.0, ≥ 10 отзывов).<br>5. Система применяет промокод (доступность, VIP-only, срок).<br>6. | 3 | Пользователь/внешние системы | Получить профиль и статус пользователя | 1. `GET /api/users/{userId}` (+ под-эндпоинты status/blacklisted/active/authorized/vip). |
| 4 | Пользователь | Найти отели | 1. `GET /api/hotels/by-city`, `GET /api/hotels/top-rated`, `GET /api/hotels/{id}`. |

## 3. Нефункциональные требования

| № | Требование |
| :-: | :- |
| 1 | **Масштабируемость.** Возможность горизонтально масштабировать только критичный компонент (бронирование) при пиковых нагрузках, а не весь монолит. |
| 2 | **Надёжность / отказоустойчивость.** Падение одного домена (например, отзывов) не должно ронять весь поток бронирования: таймауты, ретраи, circuit breaker, деградация (fallback). |
| 3 | **Независимость разработки.** Два отдельных домена могут развиваться разными командами/ветками без блокировок. |
| 4 | **Ограниченные ресурсы команды.** Состав: 2 Java-разработчика, 1 архитектор (пишет код), 1 фронтенд, 1 DevOps, 1 тестировщик, 1 PM. Решение должно быть без избыточного стека. |
| 5 | **Наблюдаемость.** Централизованные логи, сквозная трассировка и метрики (в инфраструктуре уже есть Docker и Kafka; планируется Kubernetes). |
| 6 | **Обратная совместимость API.** Старые клиенты/фронтенд не должны ломаться на этапах перехода; используется паттерн Strangler Fig. |
| 7 | **Стоимость.** Поэтапный переход малыми шагами, каждая итерация даёт рабочий, тестируемый инкремент. |
| 8 | **Безопасность.** Доступ к данным пользователя и операциям бронирования должен проверяться (ACL), а не доверять произвольным `userId` без контроля. |
| 9 | **Консистентность данных.** Временное согласованное состояние между вынесенным сервисом и монолитом (shared-database сначала, затем разделение схем). |

## 4. Ключевые проблемы

### 4.1. Проблемы, заявленные в бизнес-контексте (`architecture/context.md`)

1. **Сложность сопровождения** - любое изменение требует понимания всей кодовой базы.
2. **Низкая масштабируемость** - нельзя масштабировать только бронирование.
3. **Невозможность гибкой разработки** - команды не автономны, CI/CD медленный.
4. **Ограничения фронтенда** - универсальный REST, нет BFF-слоя.
5. **Сложность запуска новых фич** - высокий риск из-за связанности.

### 4.2. Проблемы, найденные в ходе анализа кода

Эти проблемы в описании монолита не заявлены, но являются архитектурно значимыми.

1. **Синхронная цепочка вызовов в ядре бизнеса.** `BookingService.createBooking()`
   вызывает 4 сервиса + БД строго последовательно и синхронно
   (`BookingService.java:42-62`). Нет таймаутов, ретраев, развязки через события.
   Единичный сбой в любом домене (например, в отзывах) приводит к полному отказу
   бронирования → прямой риск для выручки.

2. **Скрытая кросс-доменная связность.** `PromoCodeService` зависит от
   `AppUserService` (проверка VIP-статуса, `PromoCodeService.java:30-34`). При
   выносе домена промокодов придётся либо прокидывать вызов в монолит, либо
   кешировать статус пользователя. Эта зависимость не видна на уровне
   контроллеров и упускается при декомпозиции «по контроллерам».

3. **Монолитный конвейер валидаций в BookingService.** Вся бизнес-политика
   (что бронировать можно, а что нет) сосредоточена в одном классе
   (`BookingService.validateUser/validateHotel`): это и есть точка, которую следует
   декомпозировать в первую очередь.

4. **Неверная семантика ошибок.** Отклонённые бронирования возвращают **HTTP 500**
   (выброс `IllegalArgumentException` при отсутствии `@ExceptionHandler`), хотя по
   смыслу это 4xx (403/409/422). Подтверждено тестами `regress.sh` и ручными
   запросами в `test-log.txt`.

5. **Отсутствие безопасности на уровне API.** Нет аутентификации/авторизации:
   `GET /api/users/{userId}` возвращает персональные данные без проверки.
   Архитектура-«to-be» должна заложить ACL.

## 5. Опции решений

### Вариант A. Оставить монолит, улучшить его внутри (refactor-in-place)

- **Дизайн:** разнести пакеты по доменам, ввести интерфейсы-порты, корректные HTTP-коды.
- **Плюсы:** минимальные затраты, ничего не разворачивается.
- **Минусы:** не решает масштабирование, изоляцию сбоев и независимость команд.
  Проблемы 1-3 из 4.1 остаются.

### Вариант B. «Big Bang» переписывание в микросервисы

- **Дизайн:** сразу вынести все 5 доменов, разделить БД, построить сетевой слой.
- **Плюсы:** целевая архитектура «сразу».
- **Минусы:** для команды из 5-6 человек это высокий риск и долгий простой
  функциональности; противоречит требованию №6 (обратная совместимость). Не
  подходит по ресурсам.

### Вариант C. Strangler Fig - постепенный вынос по одному домену (выбран)

- **Дизайн:** монолит остаётся фронтом (REST-фасад), выбранный домен выносится в
  отдельный сервис за интерфейс-порты (антикоррупционный слой). Внешний API
  сохраняется; трафик переключается фича-флагом; регрессионные тесты прогоняются
  на каждом шаге (до/после). Данные домена в итоге переезжают в собственную БД.
- **Плюсы:** каждый инкремент работоспособен и тестируем; риск минимален; учтены
  ограничения команды.
- **Минусы:** длительное время на полный переход; временная сложность (двойная
  реализация, синхронизация данных) - управляемый компромисс.

**Вывод:** выбирается **Вариант C** как единственный, удовлетворяющий одновременно
нефункциональным требованиям и ресурсным ограничениям.

## 6. Первый модуль для выноса: **Booking**

### Почему Booking, а не «самый простой» (User)

| Критерий | Booking | User (лист, без зависимостей) |
|---|---|---|
| Бизнес-ценность | **Критический поток денег** - создание бронирований | Вспомогательные данные |
| Масштабируемость (пиковая нагрузка) | **Максимальная**, именно на бронирование | Низкая |
| Связанность | **Хаб** → тянет User/Hotel/Review/Promo | 0 зависимостей |
| Выигрыш от декомпозиции | Освобождает монолит от самого сложного оркестратора | Минимальный |
| Риск | Средний, но гасится портами и фича-флагами | Низкий |

Обоснование:

1. **Это «сердце» бизнеса.** Booking - именно тот поток, который страдает от
   синхронной цепочки (4.2.1) и на который приходится пиковая нагрузка.
   Вынеся его, мы получаем максимальную бизнес-ценность на единицу затрат.
2. **Изоляция сбоев.** Пока Booking внутри монолита, отказ любого домена (отзывы,
   промокоды) роняет всю операцию. В микросервисе цепочка становится явной и
   защищается (сброс кеша-фолбэка отказавшего сервиса, ретраи) без влияния на
   остальные эндпоинты монолита.
3. **Самый сложный оркестратор уходит первым** - это максимально снижает
   сложность монолита и, следовательно, риск любых будущих изменений.
4. **Зависимости Booking - это листья.** Зависимые домены (User, Hotel, Review,
   Promo) автономны, и их легко оставить в монолите, отдав наружу только то, что
   нужно Booking (небольшие API-срезы). Это типичный сценарий для Strangler Fig.

## 7. Решение. Целевая архитектура (to-be)

Диаграммы C4 (Context, Container) приведены в `../diagram/`.
Ключевые принципы:

1. **BFF / GraphQL-фасад** перед клиентами - единая
   точка для фронтенда, скрывает внутреннюю топологию, снижает число round-trip.
2. **`booking-service` - отдельный сервис** со своей базой (`booking`-схема),
   принимающий создания бронирований. Синтаксис и контракт `/api/bookings`
   сохраняются.
3. **Антикоррупционный слой (ports & adapters) в монолите:** `BookingService`
   перестаёт вызывать сервисы монолита напрямую; вместо этого используются
   интерфейсы-порты, реализация которых в фазе миграции обращается к вынесенному
   сервису (REST/gRPC), а в дальнейшем - к реальным микросервисам.
4. **Синхронные RPC для запросов + Kafka для событий:**
   - запросы (валидации отеля/пользователя/промокода) - синхронно с таймаутами,
     ретраями и circuit breaker (Resilience4j). Кеш малотривиальных данных,
     чтобы не нагружать монолит;
   - события (`BookingCreatedDomainEvent`) - в Kafka для реактивных подписчиков
     (аналитика, обновление агрегатов отеля и т.д.). Kafka уже есть в стеке.
5. **Декомпозиция данных по шагам:** сначала общая БД (shared-database), чтобы
   не блокировать выкат; затем → own-schema, затем → own-database
   (management-driven, согласованная миграция через скрипты/ликвибазу, бэкапы).
6. **Таймауты/деградация:** если монолит не отвечает на вспомогательный запрос,
   booking-service применяет кеш/фолбэк и логирует деградацию.
7. **Область видимости данных:** ACL и авторизация закладываются в фасаде.

### Конечное целевое состояние

```
Клиенты (Web / Mobile) → BFF/GraphQL Gateway
   ├── booking-service ──(own DB)──
   ├── user-service    ──(own DB)──
   ├── hotel-service   ──(own DB)──
   ├── promo-service   ──(own DB)──
   └── review-service  ──(own DB)──
Все обмениваются через REST/gRPC (запросы) и Kafka (события).
```

## 8. План миграции (Strangler Fig)

| Фаза | Действия | Критерий выхода |
|---|---|---|
| **0. Базовая линия** | Запуск монолита + БД; прогон регрессионного стенда (`test/regress.sh`); фиксация контрактов API как формальных (OpenAPI) | Все тесты зелёные |
| **1. Стабилизация монолита** | Корректные HTTP-коды ошибок (4xx), заполнение `createdAt`, фиксация схемы БД (миграции вместо ddl-auto=create) | Код-стабильный монолит без снижения качества API |
| **2. Порты/адаптеры в Booking** | В монолите `BookingService` переводится на интерфейсы-порты (User/Hotel/Review/Promo) с реализацией через REST-клиенты к самим себе (in-process сначала) | Монолит работает через порты; регрессия зелёная |
| **3. Вынос booking-service** | Создание отдельного Spring-сервиса (REST + gRPC `BookingProto`); переезд данных `booking` в own-schema; монолит сохраняет REST-фасад `/api/bookings`, проксируя запросы в booking-service | Сервис развёрнут; фасад отдаёт те же ответы |
| **4. Переключение трафика** | Фича-флаг / роутинг gateway направляет часть трафика на новый сервис; канареечный выкат | Канареечный и fallback-сценарии проходят; регрессия зелёная на обоих путях |
| **5. Вынос следующих доменов** | Review → Hotel → Promo → User по той же схеме (порты → сервис → own-DB → переключение) | Каждый домен вынесен, данные разделены |
| **6. Полное избавление от монолита** | Удаление внутренних реализаций вынесенных доменов; монолит/старый код утилизируется; остаётся набор микросервисов + BFF | Монолит выведен из эксплуатации |

## 9. Альтернативы (детально)

1. **Разделение по слоям (Controller → Service → Repository) в микросервисы**
   («вертикальные срезы по слоям») - создаёт сервисы с той же связанностью, но с
   сетевыми вызовами. **Отклонено:** наследует все проблемы монолита + добавляет
   сетевые задержки.
2. **Event-driven с самого начала (Saga / CQRS + Event Sourcing)** для
   бронирования - мощно, но избыточно для текущей команды и объёма данных.
   **Отклонено** для первого шага; принято частичное использование Kafka
   (события после создания бронирования), чтобы не усложнять транзакционный
   контур.
3. **Monolith-first (модульный монолит) перед микросервисами** - возврат к
   Варианту A, отложенное решение проблем масштабирования; не устраняет пиковую
   нагрузку на Booking.

## 10. Недостатки, ограничения и риски выбранного решения

| № | Риск / ограничение | Митигация |
|---|---|---|
| 1 | **Временная двойная реализация** (порты в монолите + новый сервис) повышает объём кода | Строгий контракт (OpenAPI/gRPC), автотесты на оба пути |
| 2 | **Разделение БД** - риски целостности и миграции данных | Миграции версионируются; этап own-schema; бэкапы; тесты на фикстурах |
| 3 | **Больше инфраструктуры** (Kafka, Kubernetes, observability) при малой команде | Прагматичный минимальный стек; постепенное внедрение |
| 4 | **Отсутствие безопасности в монолите** (персональные данные без ACL) | Закладывается в BFF-фасад и gRPC |
